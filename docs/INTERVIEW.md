# 面试问答口径

> 本文按"面试官会怎么问"组织，每问给出**推荐回答骨架 + 可深挖的细节**。
> 所有数据都来自本项目的真实验证结果，不是编造的数字。

---

## 一、项目介绍（1 分钟版）

> 这是一个面向高校教务和学生学业规划的前后端分离系统，解决的是"选课、成绩、毕业进度、学业预警
> 分散在多个 Excel 和老师经验里"的问题。
>
> 技术上后端用 FastAPI + SQLAlchemy 2.0 + MySQL 8.0，Redis 做缓存和分布式锁，
> 前端是 Vue3 + TypeScript + Element Plus。
>
> 我主要负责后端核心，包括登录鉴权、专业班级、学期开课、智能选课、课表、成绩和课程推荐。
>
> 做得最有价值的两块：一是**选课并发控制**，用"Redis 幂等 + 分布式锁 + MySQL 行锁"三重防线，
> 实测 40 个线程抢 3 个名额，正好 3 人成功、计数器与真实记录数完全一致，没有超卖；
> 二是**把教务经验算法化** —— 选课校验做成 9 条可配置规则的责任链，学业风险做成五维加权模型，
> 管理员在后台调参数就能改策略，不用发版。

### 2 分钟版补充
在 1 分钟版之后补三点：
1. **规模**：15 张表 / 65 个接口 / 10 个业务模块，演示数据 270 名学生、41 门课程、3280 条选课记录、3200 条成绩；
2. **工程严谨性**：写了并发压测脚本和 34 项断言的端到端冒烟测试，都是可复现的；
3. **算法落地**：推荐用协同过滤 + 规则因子融合，专门处理了新生冷启动；风险识别做了可解释性。

## 二、必问问题：选课并发

### Q1：选课为什么会有并发问题？具体是什么场景？

**回答骨架**：选课是典型的"秒杀"场景。
一门热门课容量 60，开放选课的瞬间可能有几百人同时点，多个请求同时读到 `selected_count = 59`，
各自 `+1` 写回，结果 60 个名额卖出 65 份 —— 这就是超卖。
除此之外还有两类隐蔽的并发问题：同一学生双击提交产生两条选课记录；两个请求同时选"时间冲突的课程"，
各自校验时都看不到对方，结果都通过了。

### Q2：你怎么解决的？

**回答骨架**：三重防线，从粗到细。

| 层次 | 手段 | 解决什么 |
| --- | --- | --- |
| 第一层 | Redis 幂等键 `SET NX EX 60` | 用户双击/网络重试造成的重复提交，请求还没到数据库就被挡掉 |
| 第二层 | Redis 分布式锁 `SET NX PX` + Lua 释放 | 多实例部署时同一教学班的请求在入口排队，降低数据库锁争用 |
| 第三层 | MySQL `SELECT ... FOR UPDATE` 行锁 | **真正保证正确性**：拿到最新计数后 read-modify-write |
| 兜底 | 唯一约束 `UNIQUE(student_id, course_id, semester_id)` | 就算前面都失效，数据库层也不会出现脏数据 |

**可深挖的细节**：
- 幂等键的内容是 `student_id + offering_id + 前端生成的随机串`，TTL 60 秒，请求处理完释放；
- 分布式锁的释放用 Lua 脚本校验持有者（`if redis.call('get',KEYS[1])==ARGV[1] then del`），
  避免"锁超时后误删别的请求的锁"；
- 最终一致性靠的是数据库行锁，Redis 那两层是性能优化与体验优化，**去掉它们功能依然正确**，
  这个分层是有意设计的。

### Q3：为什么必须用 `SELECT ... FOR UPDATE`？普通 SELECT 不行吗？

**回答骨架**：不行。MySQL 默认隔离级别是 REPEATABLE READ，
普通 `SELECT` 读的是事务开始时的**一致性快照**，在整个事务里看到的值都不变。
如果用它拿到 `selected_count = 59`，另一个事务已经提交成 60，你基于 59 算出来的 60 就是错的。

`SELECT ... FOR UPDATE` 做两件事：一是**读最新已提交版本**（当前读），二是**加排他锁**，
其他事务在这一行上必须排队。所以"读最新 + 串行化"两个问题一起解决了。

### Q4：加锁顺序为什么重要？

**回答骨架**：为了防死锁。这个项目里一次选课要锁两行：学生行和教学班行。
如果事务 A 先锁学生 1 再锁教学班 10，事务 B 先锁教学班 10 再锁学生 1，
A 等 B 释放教学班、B 等 A 释放学生 —— 互相等待，MySQL 直接报 1213 Deadlock。

解决办法就是**全局统一加锁顺序**（本项目固定为"先学生后教学班"），
所有事务按同一顺序申请锁，就不会出现循环等待。

即便如此我还是保留了死锁重试：捕获 1213/1205 后回滚重试最多 3 次。
生产环境里"能自愈"比"假设永不出错"更现实 —— 而且锁等待超时也可能是网络抖动导致的。

### Q5：为什么不锁学生行？只锁教学班行行不行？

**回答骨架**：会漏掉"时间冲突"的并发场景。
学生同时提交两门时间冲突的课，两个事务分别锁的是两个不同的教学班行，互不阻塞，
各自都读不到对方的选课记录，冲突检测就都通过了。
锁住学生行后，同一学生的选课被串行化，第二个请求能看到第一个已提交的记录，冲突才会被正确拦下。

这是"锁的粒度要覆盖到不变量的范围"这个原则的体现。

### Q6：为什么把已选人数做成计数器字段，而不是每次 `COUNT(*)`？

**回答骨架**：性能与锁粒度。
`COUNT(*)` 需要在 `t_enrollment` 上做范围统计，锁的粒度是整个索引区间，并发一高就互相阻塞；
把计数放在 `t_course_offering` 的一行上，锁的粒度收敛到单行，吞吐量高很多。

代价是引入了"计数器与真实记录数可能不一致"的风险，所以要保证所有增减都在行锁下做 ——
退课的时候同样 `FOR UPDATE` 之后再 `-1`，否则会出现"退了课但名额没还回去"。
压测脚本里专门断言了 `selected_count == 真实记录数`，就是为了守住这个不变量。

### Q7：Redis 挂了怎么办？

**回答骨架**：所有 Redis 调用都包了 try/except 做 **fail-open 降级**：
- 缓存读写返回 None → 直连数据库；
- 分布式锁跳过 → 只剩 MySQL 行锁（性能下降但结果依然正确）；
- 黑名单校验返回 False → 登出后 token 保留到自然过期。

设计原则是**中间件故障不该拖垮核心业务**。因为正确性只依赖数据库行锁和唯一约束，
Redis 只承担性能优化职责，所以可以安全降级。
本机演示时 Redis 没启动过，整个系统跑得好好的，包括 34 项端到端测试全绿，就是这套降级生效的证明。

### Q8：压测怎么做的？结果如何？

**回答骨架**：写了个脚本，40 个线程用 `threading.Barrier` 对齐后同时发起选课，
每个线程独立数据库连接和事务，目标是一个容量只有 3 的教学班。

```
抢课成功      ：3 人
因满员被拒    ：33 人
因其他原因被拒：4 人   ← 时间冲突，属于规则正确拦截
教学班计数器  ：3
数据库记录数  ：3
结论：未超卖 ✅
```

脚本最后会断言"成功人数 ≤ 容量"且"计数器 == 真实记录数"，
结果不一致会直接报超卖 ❌，所以这个结论是可复现、可回归的。

## 三、规则引擎

### Q9：为什么要把选课校验做成规则引擎？直接写 if-else 不行吗？

**回答骨架**：一开始确实是 if-else，问题出在**改需求**。
教务的需求经常变：毕业季想把学分上限从 30 调到 32、某学期想临时关闭"已修读课程"的校验、
新生入学想限制只能选公共课。每次都要改代码、发版。

所以抽成规则引擎：每条规则一个类（策略模式），元数据存数据库表，
引擎按优先级加载启用的规则依次执行（责任链），参数存 JSON。
管理员在后台勾选/改参数，清一下缓存即刻生效。

这本质上是**把业务策略从代码里搬到了配置里**，符合开闭原则 —— 新增规则只要实现一个 `check()` 方法再注册。

### Q10：规则引擎为什么不做短路？

**回答骨架**：这是个刻意的设计决策。
如果第一条规则拦住就立刻返回，学生只能改一次试一次，体验很差，客服也会被问爆。

所以我让引擎**把所有规则跑完**，再统一汇总。前端拿到的是完整诊断报告：
"时间冲突（和《线性代数》撞了）、学分超上限、先修课没修"，一次讲清所有问题。

代价是多算几条规则，但规则都是内存计算（状态快照已经装配好了），成本可以忽略，体验收益很大。

### Q11：规则怎么保证不 N+1 查询？

**回答骨架**：规则本身是**纯函数** —— 它只读一个 `RuleContext` 对象，不查库、不写库。
所有需要的数据由 `build_academic_state()` 一次性装配成内存快照：
本学期已选课程、时间占用块、历史最好成绩、已通过课程集合、当前学分、累计 GPA 等。

这样做有三个好处：一次选课从 N 条 SQL 降到常数级；
规则可以脱离数据库做单元测试；规则逻辑清晰，不用关心数据怎么来的。

列表接口（可选课程列表）也是同理：装配一次快照，然后对每个教学班跑规则，而不是每个教学班查一次库。

### Q12：规则有哪几条？举几条讲讲

**回答骨架**：9 条，分两个级别。

BLOCK（硬性拦截）：选课时间窗口、教学班开放状态、专业年级范围、同课重复选、先修课、时间冲突、学分上限。
WARN（仅提示）：已修读课程（已及格提示走重修通道）、毕业缺口匹配度（临近毕业还选通识课，提示优先补必修）。

**时间冲突检测**的算法可以讲细一点：两个时间段冲突要同时满足三个条件 ——
同一天、节次区间重叠、周次区间重叠。区间重叠用 `not (a.end < b.start or b.end < a.start)` 判断，
比自己写一堆 if 更简洁也不容易漏边界（相等的情况算重叠，这是有意的）。

**学分上限**这条里我还放了一个业务决策：累计 GPA 低于 1.5 的学生，学分上限自动下调 6 分。
这不是单纯的校验，而是把教务的管理决策算法化了。

## 四、推荐算法

### Q13：推荐是怎么做的？

**回答骨架**：混合推荐，四步链路。

```
候选集 → [召回] 协同过滤 → [过滤] 规则引擎 → [重排] 多因子打分
```

- **候选集**：当前学期开放、有余量、未修读过、课程有效；
- **召回**：Item-CF 和 User-CF 加权（0.6 : 0.4）。
  评分矩阵用成绩 `final_score/100` 作显式反馈，只选课未出成绩的记 0.6 作隐式反馈；
  Item-CF 算课程间余弦相似度（保留 Top20 邻居），User-CF 找 TopK 相似同学；
- **过滤**：用同一套规则引擎把不可选的剔除掉，**保证推荐出来的课一定选得上**；
- **重排**：`final = 0.55 × CF分 + 0.45 × 规则分`，
  规则因子包括毕业缺口（35 分，权重最高）、专业匹配、时间可行性、年级适配、选课热度。

### Q14：为什么不用纯协同过滤？

**回答骨架**：两个硬伤。

一是**冷启动**：新生在第一学期没有任何成绩和选课记录，余弦相似度算不出来，推荐结果为空。
实测 2026 级新生在纯 CF 下是 0 条推荐。

二是**没有业务约束**：协同过滤算出来的是"相似度"，它不知道"这门课你没修先修课""这门课和你的课表冲突"。
推一堆选不上的课，用户直接就不信这个功能了。

所以采混合策略：CF 负责个性化排序，规则负责业务约束和冷启动兜底。
检测到 CF 无信号时改用课程热度做先验分，并在推荐理由里明确写"新开设课程，暂无历史数据"。
实测新生能正常拿到 5 条推荐。

### Q15：推荐效果怎么评估？怎么保证可解释？

**回答骨架**：可解释性这块我做得比较实。
每条推荐都生成人能读懂的推荐理由，比如"修过《计算机组成原理》的同学也常选这门课；
该类别仍缺 48 学分，修读优先级高"。

还提供了 `GET /recommend/explain/{course_id}` 接口，返回完整打分明细：
协同过滤分多少、规则分多少、各自哪些因子贡献的。

推荐系统落地最大的阻力其实是"黑箱" —— 学生看到推荐会想"凭什么推这个给我"。
把算法结论翻译成人话，比提升 1% 的准确率更能换来用户信任。

如果有离线评估条件，我会用留一法：把学生最后一次选课藏起来，看推荐 Top10 的命中率。
当前数据量（270 学生 / 41 课程）不足以做严格评估，这是个已知的局限。

### Q16：性能上怎么优化？

**回答骨架**：
- 相似度矩阵是 O(n²) 计算，课程量级（千门）内可接受，算完缓存进 Redis TTL 10 分钟；
- 推荐结果按 `student_id + 参数` 缓存 5 分钟，选课/退课/成绩录入时主动失效缓存；
- 课程相似度矩阵每门课只保留 Top20 邻居，控制内存；
- 真实生产环境应该把矩阵计算改成**离线任务**（Spark 或定时任务）预计算写回 Redis，
  在线只做查表和排序，把 O(n²) 从请求链路里彻底摘出去。

## 五、学业风险识别

### Q17：学业风险怎么量化？

**回答骨架**：五个维度各自打分（0-100），按权重合成综合风险分。
权重是：挂科 0.35、绩点 0.25、学分落后 0.20、成绩下滑 0.10、毕业风险 0.10。

- 挂科分 = 40 + 挂科门数×12 + 挂科学分占比×60（门数和严重程度都考虑）；
- 绩点分 = (2.5 - GPA)/2.5×100 + 班级排名百分位×20（绝对水平和相对位置结合）；
- 学分落后：实际学分低于"按学期进度应得学分"的 85% 触发；
- 成绩下滑：最近两学期 GPA 环比下降 ≥ 0.3；
- 毕业风险：缺口学分 > 剩余学期 × 22 学分（按线性外推估算）。

综合分映射等级：≥60 高风险，≥40 中风险，其余低风险。
阈值是按风险分的分位数标定的而不是拍脑袋定的 —— 实测最高分 63.3、P90 是 44.7，
如果按常见的 80 分阈值，高风险永远是空集。真实上线后应该随数据分布定期回归标定。

### Q18：为什么用加权而不是机器学习模型？

**回答骨架**：三个现实约束。

一是**没有标注数据** —— 谁是"高风险学生"没有历史标签，做不了监督学习。
二是**数据量小**，几百个学生训不出可靠模型。
三是**可解释性要求高** —— 辅导员拿这个结果去和学生谈话，必须能说清"为什么判你高风险"，
一个黑箱模型的输出在和教育场景里没法直接用。

所以先用规则化的加权模型，等积累了几年"预警—干预—结果"的数据，
再考虑用逻辑回归或 GBDT 做风险预测，把当前模型作为特征。这是个合理的演进路径。

### Q19：怎么避免预警刷屏？

**回答骨架**：用 upsert 幂等落库。
`t_risk_alert` 上有索引 `(student_id, risk_type, semester_id)`，
扫描时先查"同一学生 + 同类型 + 同学期 + 未处理"的记录是否存在：
存在就更新分数和原因，不存在才插入。

这样每天跑定时扫描也不会产生重复记录，辅导员看到的始终是最新的状态。
处理过的记录（status = HANDLED）不参与判重，下次扫描会新开一条，方便统计"复发"。

## 六、工程细节追问

### Q20：鉴权怎么做的？为什么用 JWT？登出怎么办？

**回答骨架**：JWT + bcrypt + RBAC。

- 密码用 bcrypt 加盐哈希（rounds=12），数据库永不存明文；
- token 用 HS256 签名，payload 带 `sub`（用户 id）、`role`、`jti`、`exp`；
- FastAPI 用依赖注入（`Depends`）做鉴权，`require_admin` / `require_student` 这类依赖
  可以直接写在路由函数签名里，不侵入业务代码。

JWT 的问题是无状态、签出去就撤不回。我用 `jti` + Redis 黑名单解决：
登出时把 `jti` 写进 Redis，TTL 设成 token 的剩余有效期（自动清理不堆积），
鉴权时先查黑名单，命中就返回 401。

### Q21：怎么防止越权（水平权限问题）？

**回答骨架**：学生接口**一律不接受前端传 student_id**，只从 token 反查当前登录学生的档案。

```python
def get_current_student(db, user) -> Student:
    if user.role != UserRole.STUDENT:
        raise PermissionError_("该接口仅供学生使用")
    return db.scalar(select(Student).where(Student.user_id == user.id))
```

这是个典型的 IDOR（不安全的直接对象引用）防护。很多项目写 `GET /grades?student_id=5`，
只要把 5 改成 6 就能看别人成绩。
原则是**权限校验依赖服务端身份，不依赖客户端参数**。

另外前端路由也按 `meta.roles` 做了拦截，但那只是体验层，真正的安全边界在后端依赖注入。

### Q22：成绩表为什么和选课表分开？GPA 怎么算？

**回答骨架**：选课是过程数据、成绩是结果数据，生命周期不同。
分开后重修不会覆盖历史成绩 —— `attempt_no` 记录第几次修读，同一门课"第一次 52 分、第二次 78 分"
的完整轨迹保留下来了，成绩单可以完整回溯。

GPA 用**学分加权平均**而不是算术平均：3 学分的专业课和 1 学分的通识课影响应该不同，
否则会影响保研和评奖的公平性。公式是 `Σ(绩点 × 学分) / Σ学分`。
重修课程只取**通过的那一次**计入，避免刷绩点。

绩点用 4.0 制分段映射：≥90 → 4.0，85-89 → 3.7，82-84 → 3.3 …… <60 → 0。

### Q23：有没有遇到性能问题？怎么排查的？

**回答骨架**：有，主要是 N+1。
最早的可选课程列表接口是逐个教学班查先修课，30 个教学班就是 30 次 SQL。
优化方式是先把所有关联数据批量查出来（`selectinload` 或 `IN` 查询），
在内存里建映射表（`{course_id: [prereqs]}`），循环里只查内存。

另一个是长连接问题：MySQL 默认 `wait_timeout` 8 小时，
连接池里的空闲连接被服务端断掉后，客户端不知道，下次用就报
"MySQL server has gone away"。解决方式是连接池开 `pool_pre_ping`（取连接前先 ping）
和 `pool_recycle=3600`（1 小时后强制重建）。

### Q24：事务边界怎么控制的？

**回答骨架**：FastAPI 用 `get_db` 依赖（yield 形式）管理 Session 生命周期：
请求开始建 Session，正常结束提交，抛异常回滚，最后一定 close。

但**选课这种需要精确控制锁范围的操作，我在 service 层自己管理事务**：
先在 Redis 锁内开启事务、加行锁、校验、写入、提交，整个流程原子化。
接口层只调用 `selection_service.select_course()`，不关心事务细节 ——
这样同一套逻辑能被 HTTP 接口、脚本、定时任务复用。

### Q25：接口返回结构为什么统一？

**回答骨架**：统一成 `{code, message, data}`，全局异常处理器保证任何错误都是这个结构。

好处是前端 axios 拦截器一处就能处理完所有响应：
`code === "OK"` 时返回 `data`，否则弹 message；401 自动清 token 跳登录；403 提示无权。
业务代码里不用写任何 try-catch 和错误判断。

错误码也是分层的：`code` 用业务语义（`OFFERING_FULL`、`ALREADY_SELECTED`），
HTTP 状态码用标准语义（409 冲突、401 未认证）。
前端按 `code` 做精细化处理，不依赖文案 —— 文案改了不会影响逻辑。

## 七、可能的压力追问

### Q26：如果课程容量 1 万、瞬间 10 万人抢呢？

**回答骨架**：当前方案在这个量级会崩，瓶颈在 MySQL 单行锁 —— 所有请求串行排队，
数据库连接池也会被打满。要做到这个量级需要改架构：

1. **Redis 预扣减**：库存放 Redis，用 Lua 脚本原子扣减（`DECR` 前判空），
   请求先在 Redis 层拦掉绝大多数，只有扣减成功的才异步落库；
2. **消息队列削峰**：扣减成功的请求写 MQ，后端消费者有序落库，
   把"同步扣减"变成"异步确认"；
3. **前端排队页**：返回"排队中"，轮询结果，避免用户狂点。

但要说清楚：Redis 预扣减会引入"Redis 说成功、落库失败"的一致性问题，
需要补偿机制（对账 + 定时修复），复杂度显著上升。
所以架构选择要匹配量级，高校选课（几千人同时在线）用数据库行锁完全够，也更简单可靠。

### Q27：规则引擎如果规则之间互相冲突怎么办？

**回答骨架**：当前设计是"全跑完、全部返回"，所以不会互相覆盖。
但确实有两种"冲突"需要处理：

一是**优先级语义冲突**：比如 `credit_limit` 说超限要拦、`graduation_gap` 说这课很该选。
我通过分级解决 —— 前者 BLOCK、后者 WARN，WARN 不会覆盖 BLOCK 的判定。
最终 `selectable = 所有 BLOCK 级规则都通过`。

二是**同一个业务点被多条规则覆盖**：目前靠 `priority` 控制执行顺序，
但如果未来出现真正互斥的规则，应该引入 `RuleGroup` 概念做互斥声明。
这是已知的可演进点，当前规则集还没有这个需求。

### Q28：你在这个项目里遇到的最大难点是什么？

**回答骨架**：推荐算法的冷启动，以及"推荐出来的课选不上"这个体验问题。

一开始我按标准做法实现 Item-CF，本地测试用自己的账号（有成绩）效果不错，
部门演示时用了一个新生账号 —— 推荐列表直接是空的。
那一刻才真正理解"冷启动"不是教科书上的概念，是会让功能在新用户面前直接失效的问题。

后来做了两件事：一是加规则因子做兜底，CF 无信号时用毕业缺口和课程热度给分，
保证任何用户都有推荐结果；二是把所有候选课先过一遍规则引擎，
保证推荐出来的课一定满足先修课和时间不冲突。

这次之后我的习惯变了：**新功能都要先用"最差数据"的用户试一遍**，
新用户、零数据、边界账号，而不是用自己那个数据丰富的账号。
